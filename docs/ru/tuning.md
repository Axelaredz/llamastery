# Тюнинг: методика, ловушки, законы

Движок — `tools/tune_models.py`. Он двухэтапный, и это главная причина его
ценности: дешёвый скрининг отсеивает мусор, дорогая проверка отсекает
правдоподобное, но негодное.

## Два этапа

1. **Скрининг** — `llama-bench` / `llama-sweep-bench` на коротком контексте.
   Дёшево, отсекает очевидно слабые комбинации `n-cpu-moe` × `ubatch` × `t`.
2. **Валидация** — живой `llama-server`: полный контекст, реальный KV, замер
   свободной VRAM, retrieval-тест (игла в стоге) на коротком и глубоком
   контексте, проверка качества драфта.

Артефакты каждого прогона: `~/.config/llama/tune-results/<этап>/<время-pid>/`
— `results.json` (машиночитаемо), `screening.json`, `run-NNN.log`.

`results.json` и есть то, что `llamastery ingest` собирает в `measurements.json`.
Поля, которые стоит читать:

| Поле | смысл |
|---|---|
| `short.gen_tps` / `deep.gen_tps` | скорость генерации на 4k и на полном контексте |
| `short.prefill_tps` | скорость заливки |
| `min_observed_free_mib` | минимум свободной VRAM за прогон — главное число |
| `needle_ok` | прошёл ли retrieval-тест (модель не «сломалась» на длинном контексте) |
| `ok` / `error` | выдержал ли запуск, с причиной |
| `config`, `config_extra` | полный набор флагов кандидата |

Из замеров берётся **худший**, а не средний: планировать надо по худшему.

## Что тюнер не делает

* Не подбирает `c` — это решение пользователя, а не поиск по сетке.
* Не выбирает между моделями.
* Не проверяет, влезает ли несколько пресетов одновременно — это `llamastery budget`.

## Ловушки, найденные на практике

### `spec-type` с несколькими значениями + внешний MTP-драфт

В сборке Faks `--spec-type ngram-mod` вместе с `--model-draft` (MTP-голова)
падает с segfault на загрузке. Внешняя MTP-голова сама по себе вдвое
медленнее (24 t/s против 48), так что `ngram-mod` без драфта — единственный
рабочий ускоритель на такой модели.

### `ubatch-size`

`ubatch-size = 2048` при 12 ГБ VRAM — известная причина OOM. Рабочее
значение 1024. Но это эвристика, а не закон: если по конкретной
конфигурации есть успешный замер, `llamastery validate` замолчит.

### `parallel`

`parallel > 1` кратно умножает KV-пул. На 12 ГБ держится `parallel = 1`.

### `mmproj` на CPU

`mmproj-offload = 0` (то есть проектор в RAM) почти не влияет на скорость
генерации — проверено на замерах: 38.9 против 38.8 t/s. В VRAM при этом
ничего не ест. Для моделей зрения на тесной карте это почти всегда лучший
выбор.

### `cache-reuse` несовместим с mmproj

Проверено по исходникам, `tools/server/server-context.cpp:1220`:

```cpp
if (params_base.n_cache_reuse) {
    params_base.n_cache_reuse = 0;
    SRV_WRN("cache_reuse is not supported by multimodal, it will be disabled");
}
```

При загрузке мультимодальной модели `cache-reuse` выключается
принудительно, с предупреждением в логе. Второй барьер (там же, ~3164):
`can_cache_reuse` требует `!slot.prompt.tokens.has_mtmd`, то есть любой
запрос с картинкой отключает reuse для этого слота.

**Важная поправка к формулировке:** ограничение относится к mmproj, а не к
`ngram-mod` и не к спекулятивному декодированию. В старой записи в models.ini
эти вещи были связаны ошибочно.

### `spec-draft-*` не действует вместе с `ngram-mod`

Проверено: `common/speculative.cpp`, функция `common_speculative_n_max()`
перебирает только **выбранные** типы из `spec->types`:

```cpp
case COMMON_SPECULATIVE_TYPE_DRAFT_SIMPLE:
case COMMON_SPECULATIVE_TYPE_DRAFT_MTP:      // и EAGLE3, DFLASH
    n_max = max(n_max, spec->draft.n_max);   // ручки draft-модели
    break;
case COMMON_SPECULATIVE_TYPE_NGRAM_MOD:
    n_max = max(n_max, spec->ngram_mod.n_max);  // свои ручки
    break;
```

Значит при `spec-type = ngram-mod` инертны `spec-draft-n-max` и
`spec-draft-p-min` — они управляют другой draft-моделью. Свои ручки у
ngram-mod: `--spec-ngram-mod-n-max` (64), `--spec-ngram-mod-n-min` (48),
`--spec-ngram-mod-n-match` (24). Пресет с `spec-draft-n-max = 1` и
`spec-type = ngram-mod` молча работает на дефолтах.

### Что даёт ngram-mod на практике

Измерено A/B на llama-upstream 0.5.0-dev, Qwen3.8 MiniPlus, 114688 токенов,
один и тот же промпт, единственная разница — строка `spec-type`:

| текст пробы | с ngram-mod | без ngram |
|---|---|---|
| lorem (повторы) | **84–92 t/s** | 26.3–26.5 t/s |
| без повторов | 30.0 t/s | 28.5–30.5 t/s |
| 4k, с повторами | 98.6 t/s | — |
| 4k, без повторов | 49.5 t/s | — |

Вывод: на повторяющемся тексте (код, шаблоны, диалоги) ускоритель даёт
×3.2, на уникальном — ровно ноль и не вредит. Поэтому `spec-type = ngram-mod`
стоит включать точечно, под задачи с повторами, а не «всегда на всякий случай».

Методическая оговорка: проба тюнера (игла в стоге) и проба `probe` дают
разные числа на одном пресете — 48 против 26.5 t/s. Это разные задачи, а не
расхождение замеров: сравнивать можно только внутри одной методики. Именно
поэтому A/B выше сделан `probe` против `probe`.

### Как работает `--n-cpu-moe`

Не числовое поле в params, а послойные override буферов
(`common/arg.cpp:2607`): для каждого слоя `i < N` добавляется
`llm_ffn_exps_block_regex(i)` в `tensor_buft_overrides` с принудительным
CPU-буфером. Поэтому поиск по `n_cpu_moe` в коде ничего не находит — искать
надо `tensor_buft_overrides` / `ffn_exps`.

Измеренное влияние на свободную VRAM (Tiel, c=114688, b=2048, прогоны с
`ok=True`): moe24 → 2963 MiB, moe32 → 5028, moe40 → 7129. Наклон
258-263 MiB на слой. Аналитическая доля весов экспертов (~0.978) завышает
эффект примерно на 13%, отсюда коэффициент `offload_realization = 0.89`,
который `llamastery calibrate --from-tune` подбирает автоматически.

### Antispam

`repeat-last-n = 256` + `repeat-penalty = 1.02` — рабочая связка против
зацикливания. При порче JSON или tool-call снижать до 1.05, ниже бесполезно.

## Закон деградации скорости

Раньше в шапке models.ini было записано `tg(D) = 1000 / (16.1 + 0.0025·D)`.
**Формула неверна**: при D = 114688 она даёт 3.3 t/s, тогда как в той же
шапке замерено 32.5 t/s — коэффициент занижен примерно в 20 раз.

Переподгонка по четырём замерам Tiel-Coder (128k, RTX 3060, без ngram):

| D | измерено |
|---|---|
| 9 864 | 48.6 t/s |
| 32 327 | 42.1 t/s |
| 63 932 | 36.1 t/s |
| 114 012 | 32.5 t/s |

даёт `tg(D) = 1 / (0.01961 + 9.786e-8 · D)`:
8k → 49.0, 32k → 43.8, 65k → 38.4, 114688 → 32.4 t/s.

**Но опираться надо на замеры своей модели, а не на формулу.** У семейства
Qwen3.8 собственный замер при 114688 — 39-41.5 t/s, что выше, чем predicts
фит для Tiel. Закон годится для порядка величин и для сравнения двух
конфигураций на одной модели, но не для переноса между моделями.

Практическое следствие: **удвоение контекста стоит примерно 1 t/s** на
больших глубинах. Поэтому 128k-пресет для длинных сессий почти ничего не
теряет по скорости.

## Артефакты замера

* Замер prefill на прогретом кэше даёт ложно высокие числа. Реальный
  холодный prefill 65k занимает ~50 минут (~20 t/s).
* Приёмка драфта 1.00 — артефакт на повторяющемся промпте, не верить.
  На разнообразном тексте приёмка 0.93.
* Первый запрос сессии драфт не ускоряет (индекс пуст).

## Ограничения тюнера, о которых стоит знать

* **Проверка извлечения факта бьёт reasoning-модели.** Тюнер просит вставить
  секрет в длинный промпт и ждёт его в ответе за 64 токена
  (`--n-predict`). Модели с `<think>` тратят весь бюджет на рассуждение,
  ответ пустой, `finish_reason: length` — и прогон заворачивается, хотя
  по скорости он отличный. Лечится `--n-predict 256`. Отличать «модель
  плохая» от «модель думает» нужно по `gen_tps`, а не по `ok`.
* **Глубокая фаза дорогая.** На 114688 холодный prefill занимает десятки
  минут, поэтому `--deep --apply` на 128k — это часы. Практическая
  замена: подобрать параметры тюнером на коротком контексте, а скорость
  на реальной глубине снять отдельно — `llamastery probe --tokens 110000`
  на живом сервере. Это дешевле и измеряет именно то, что нужно.
* **Список допустимых ключей расширяется схемой сборки.** Тюнер берёт
  флаги из `--help` целевого бинаря, поэтому пресет с форковыми флагами
  (`load-mode`, `ctx-checkpoints`, `no-mmproj-offload`) проходит, а знание
  не дублируется в коде тюнера.

## Порядок действий при подборе пресета

1. `llamastery schema --grep <подстрока>` — проверить, что флаг вообще есть
   в этой сборке (форки добавляют свои, а `--draft`/`--draft-min` в новых
   версиях объявлены удалёнными).
2. Зафиксировать `c` (ёмкость задачи) и модель.
3. `llamastery budget <секция>` — прикинуть память, при нехватке снижать
   `n-cpu-moe` (самый сильный рычаг на MoE) или `c`.
4. `llamastery tune ... --extra deep` — тюнер переберёт `n-cpu-moe`/`ubatch`/`t`.
5. `llamastery ingest --apply` — зафиксировать замеры.
6. `llamastery budget` по всем секциям — проверить, что несколько пресетов
   влезают одновременно под `--models-max`.
